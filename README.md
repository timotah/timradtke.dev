# Tim Radtke — Portfolio

Personal portfolio for Tim Radtke, senior full-stack software engineer.

- Vanilla JS single-page app, with Vite as the bundler
- Under 14kb gzipped (about 40–50kb uncompressed), so it arrives in one network round trip
- No frameworks, no libraries, no runtime dependencies
- Gruvbox color scheme with light and dark modes, switched by pulling a light bulb's chain.
  More themes later, and every theme has light and dark
- A bento box landing page that holds all the essential information, with click-in detail views
  for people who want more
- All content lives in `content.json`, including the resume
- Hosted on Cloudflare from day one. GitHub Pages is the fallback
- Aiming for a Lighthouse score as close to 100 as possible

## Constitution

These are the rules for the project. Any change to the site must follow them. If a rule needs to
change, edit it here first (see [Amendments](#amendments)) and then change the code. **MUST** is a
hard rule. **SHOULD** is a strong default that needs a written reason to break.

### Article I: Purpose and positioning

1. The site exists to get Tim hired. Every feature is judged by whether it helps a recruiter or
   hiring manager understand who Tim is, what he has built, and how to reach him.
2. **The bento box is the product.** The landing page MUST contain all the information a visitor
   needs. Everything behind a click is extra detail for people who are curious, never something
   they need.
3. The site is also a work sample. Its speed, size, and accessibility are part of the pitch.
4. **Positioning:**
   - Senior full-stack engineer at AMOpportunities.
   - Backend is the strength. Capable on the frontend. Works with agentic coding tools.
   - **The passion is data systems: improving availability, capacity, and efficiency.**
5. The hero has two lines stacked: the role as a small label, then a headline about data systems.
   The site's own efficiency (14kb, one round trip) is evidence for the headline, so the copy can
   point to it.

### Article II: Design principles

1. **Boring core, playful edges.**
   - Content, navigation, and section labels are conventional.
   - Personality goes into subtitles, motion, themes, the light bulb, and easter eggs.
2. **Layered progressive enhancement.** Each layer adds to the one below it, and each one still
   works if the next layer fails to load.

   | Layer | What it provides |
   |---|---|
   | 0 · HTML | A complete, readable bento. Navbar links jump to tiles. |
   | 1 · CSS | Layout, themes, and the hover link between navbar items and tiles. |
   | 2 · JS | Click-in detail views, hash routing, the light bulb, and the print-time resume. |
   | 3 · Extras | Easter eggs and transitions. |
3. **No duplicate bytes.**
   - Nothing is shipped twice. The inline JSON only carries content the HTML doesn't already
     contain.
   - Shared values like colors and spacing are defined once as CSS custom properties.
4. **Every change states its byte cost.** Each pull request lists how many gzip bytes it adds or
   removes. Deleting things counts as a feature.
5. **Privacy by default.**
   - No trackers, no cookies, and no third-party requests.
   - `localStorage` is only used for the mode and theme setting and easter egg progress.
6. **Honest claims only.**
   - Every claim is true and describes what Tim did himself.
   - Numbers are added when they can be shared publicly. Until then, describe outcomes without
     numbers, and never make up or round up a number.

### Article III: The budget

1. The built `dist/index.html`, including all of its inline CSS, JS, JSON, and SVG, MUST be
   **≤ 14,000 bytes gzipped** (`gzip -9`). This is a hard limit and the build fails above it.
2. The working target is **≤ 12,800 bytes gzipped**. That leaves room for response headers and TLS
   overhead, which share the roughly 14.6kb first round trip.
3. The uncompressed size SHOULD stay around 40–50kb.
4. We measure gzip, not brotli. Gzip is larger, so it is the honest worst case. Brotli on Cloudflare
   only gives extra headroom.
5. `404.html` is also a page someone can land on first, so it has the same 14,000-byte limit.
6. Things that don't count toward the budget: `og.png`, `resume.pdf`, `robots.txt`, `humans.txt`,
   `_headers`, and any future images that load lazily inside detail views.
7. The first view MUST NOT need a second request. That means no external CSS, JS, fonts, JSON, or
   images.

### Article IV: Content lives in JSON

1. `src/content.json` is the **single source of truth** for all copy: profile, links, tiles,
   experience, skills, focus areas, "now", and the full resume. Copy MUST NOT be hard-coded in
   HTML or JS.
2. JSON is never fetched at runtime. At build time:
   - the bento tiles are rendered into static HTML;
   - the JSON-LD `Person` block (structured data for search engines) is generated from the JSON;
   - only content that isn't already in the HTML (detail views, the full resume) is inlined as
     `<script type="application/json" id="data">`.
3. Keep the JSON lean. The structure follows what the UI needs, with no unused fields. Bento tiles
   get one line each, and longer text belongs in the detail views.
4. Titles, company names, and dates MUST match LinkedIn and `resume.pdf` exactly.

### Article V: First load and paint

1. The bento MUST render completely with no JS.
2. CSS is inline in `<head>`. JS is a single inline `<script type="module">`, which runs after the
   page is parsed and never blocks rendering. The only exception is a tiny blocking script in
   `<head>` that sets the light or dark mode before first paint, so the page never flashes the
   wrong mode.
3. No webfonts.
4. The favicon is an inline SVG data URI. That costs zero requests and avoids a 404 on
   `/favicon.ico`.
5. Layout shift (CLS) MUST be 0.
6. Animations use only `transform` and `opacity`.

### Article VI: Visual design

1. **Modern and sleek, not pretentious.**
   - Sans-serif text (`system-ui`), with monospace accents (`ui-monospace`) for labels, stack tags,
     byte counts, and small details.
   - No decoration for its own sake.
2. **Generous whitespace.**
   - Nothing feels cramped.
   - Spacing comes from a small scale of custom properties, such as `--s1` through `--s6`.
   - Tiles have consistent padding.
3. **Clear contrast between the page and the tiles.**
   - Tiles MUST be easy to tell apart from the background in both modes, through a visible change
     in color plus a border or shadow.
   - Light mode, which is the reference design, has a beige Gruvbox page background with lighter
     tiles.
   - Dark mode mirrors that with Gruvbox's dark backgrounds.
4. **No images in v1.**
   - No headshot and no screenshots.
   - Inline SVG decoration is welcome later and counts toward the budget.
   - Project screenshots are a later decision, and they would only appear in detail views, loaded
     lazily.

### Article VII: The bento layout

1. **The v1 tiles** (7):

   | Tile | Shows without clicking | Click-in |
   |---|---|---|
   | **Hero** | Name, role label, data-systems headline, location or remote status | — |
   | **Experience** | Current role at AMOpportunities and area of responsibility | Full history |
   | **Focus** | Availability · capacity · efficiency, with one line each | How Tim approaches each one, with examples |
   | **Skills** | Backend, frontend, data, infrastructure, and agentic tooling | Grouped detail |
   | **This site** | "This page is N bytes and arrived in one round trip" | How it was built and why |
   | **Now** | What Tim is currently building, learning, or reading | Optional longer note |
   | **Contact** | Email in full, plus GitHub and LinkedIn | — |

2. Project tiles get added once there are projects to show. The total stays at **8 tiles or
   fewer**. Add a tile only by merging or dropping another.
3. Every tile MUST make sense without clicking.
4. On screens at least **900×700**, the bento fits within one screen (`100dvh`). On smaller,
   zoomed-in, or landscape-phone screens, the tiles stack into one column and the page scrolls.
5. The page MUST NEVER use `overflow: hidden` on `body`, lock scrolling, or set a fixed `height`
   on the page.
6. Release check: the bento is readable on a **1366×768** laptop and a **360×740** phone.
7. The byte count on the "This site" tile is filled in at build time from the real gzip size.

### Article VIII: Navigation and SPA behavior

1. There is always a visible navbar.
   - It has links to the tile sections plus **Resume · GitHub · LinkedIn · Contact**.
   - Navbar links and tiles open the **same detail views**.
2. **Navbar items and tiles are linked visually.** Hovering a navbar item gives the matching tile
   its hover style. This uses CSS `:has()`. Keyboard focus is shown by the browser's own
   `:focus-visible` ring on the focused control rather than by reusing the hover style, because the
   browser returns focus to whatever opened a dialog and a hover-styled tile then looks like it is
   still open (see [Amendment C](#amendment-c-applied-focus-does-not-reuse-hover)).
3. Routing uses the URL hash (`/#experience`), and each route matches the `id` of its tile.
   - With JS, the hash opens that tile's detail view, so every view has a link that can be shared.
   - Without JS, the same link just scrolls to the tile.
4. Detail views use the native `<dialog>` element.
   - Focus handling and closing with Esc come for free.
   - The back button closes the dialog.
   - Long content scrolls inside the dialog.
5. The View Transitions API animates opening a tile, but only where the browser supports it.
6. Easter eggs and any future terminal or command palette are **never the only way** to reach
   something.

### Article IX: Themes and the light bulb

1. **Gruvbox is the only theme in v1**, with light and dark modes. The first visit follows the
   operating system's `prefers-color-scheme` setting.
2. **The mode switch is a light bulb in a corner of the screen.** It is always visible. Pulling its
   chain switches between light and dark, and that the chain is the switch is the hidden part.
   - The bulb glows warmly in light mode and is dim in dark mode.
   - It is a real `<button>` with `aria-label="Toggle light/dark mode"`. It works with a click, a
     tap, Enter, or Space. Dragging the chain is optional.
   - With `prefers-reduced-motion`, the chain doesn't swing and the mode just switches.
3. Every theme MUST ship **both a light and a dark mode**. A theme with only one mode isn't
   finished.
4. A theme is only a set of CSS custom properties applied through `[data-theme][data-mode]`
   selectors. Components MUST use the variables and never hard-coded colors.
5. Every theme in both modes MUST pass WCAG AA contrast for text and 3:1 for focus outlines. Check
   every Gruvbox accent against both backgrounds.
6. The visitor's choice is saved in `localStorage`.
7. More themes and a way to pick between them come later. Each new theme SHOULD cost **≤ 250
   bytes gzipped**.

### Article X: Resume and print

1. The full resume content lives in `content.json`.
2. **`resume.pdf` is made by printing the site** (Ctrl+P → Save as PDF).
   - On the `beforeprint` event, JS renders the full resume from the inline JSON into a container
     that only appears when printing. That way the resume text isn't shipped twice.
   - The print stylesheet hides the bento, navbar, bulb, and easter eggs.
3. The printed resume is one column with standard headings (Experience, Skills, Education) and
   real selectable text. URLs are printed as visible text so applicant tracking systems can read
   them.
4. **Keeping `resume.pdf` in sync is Tim's job.** After any change to `content.json`, print the
   site again and replace `public/resume.pdf`.

### Article XI: Readability for recruiters and parsers

1. Applicant tracking systems parse `resume.pdf`, not this site. The site is written for **people
   skimming quickly, search engines, and AI tools** that recruiters paste URLs into.
2. Parsers only need to understand the bento, which is in the static HTML from the first byte.
   Detail views are there for the people browsing.
3. The page uses semantic HTML with standard names (`Experience`, `Skills`, `Contact`). Jokes go in
   subtitles, never in section names.
4. The `<head>` MUST include:
   - a `<title>` with Tim's role and focus;
   - a meta description;
   - `lang` on the `<html>` element;
   - a canonical URL;
   - Open Graph tags plus a 1200×630 `og.png`;
   - the JSON-LD `Person` block with `name`, `jobTitle`, `worksFor`, `knowsAbout`, `sameAs`, and
     `url`.

### Article XII: Accessibility and browser support

1. **Accessibility:**
   - The page works fully with a keyboard.
   - There is a visible `:focus-visible` style.
   - Animation respects `prefers-reduced-motion`.
   - Anything that has no visible text gets an `aria-label`.
   - Keyboard focus is always visible through the `:focus-visible` ring. Hover styles are not
     reused for focus, because the browser returns focus to the element that opened a dialog and a
     hover-styled section then reads as "still open" while the pointer is somewhere else.
2. **Browser support follows "Baseline widely available":** features that have worked in all major
   browsers for at least 2.5 years. Newer features, such as View Transitions, are optional extras
   the site still works without.

### Article XIII: Lighthouse

1. The target is **100 in Performance, Accessibility, Best Practices, and SEO**, measured with
   Lighthouse's mobile profile.
2. For now, only the size gate (Article III) blocks a deploy. Lighthouse is a goal, not a gate.
   - Run PageSpeed Insights on the preview URL before merging changes that affect layout,
     scripts, or the `<head>`.
   - Explain any drop in the pull request.
3. Best Practices: no errors in the browser console (playful `console.log` messages are fine), no
   deprecated APIs, and HTTPS everywhere.

### Article XIV: Gimmicks and easter eggs

1. Easter eggs are encouraged, but they are additions, not features the site depends on.
2. Easter eggs MUST NOT:
   - block first paint;
   - shift the layout;
   - ignore `prefers-reduced-motion`;
   - get in the way of reading the bento.
3. **v1 ships only small easter eggs**, each SHOULD cost **≤ 500 bytes gzipped**. Candidates:
   - a console message;
   - ASCII art in the page source;
   - the tab title changing when the tab loses focus;
   - `humans.txt`;
   - a custom text selection color.
4. One larger **signature feature** (a terminal, a command palette, or a Konami code) of up to
   about 2kb gets picked later, once the real size of the site is known.
5. If the budget gets tight, easter eggs are cut first. Content and accessibility are never cut.

### Article XV: Analytics

1. v1 has **no analytics**.
2. If analytics are ever added, that requires an amendment. They MUST be cookieless, MUST load after
   first paint, and MUST be counted in the byte report.

### Article XVI: Simplicity

1. Vite is the only dev dependency. There are zero runtime dependencies and no third-party Vite
   plugins. Anything custom is a small plugin written directly in `vite.config.js`.
2. The build outputs **one self-contained `index.html`** plus the static files in `public/`.
3. Plain modern JavaScript and CSS. No TypeScript build step. JSDoc comments are optional.
4. If a feature needs an abstraction to stay manageable, it is probably too big for this site.

## Project layout

```
portfolio/
├── index.html                     # template: <head>, navbar, bento slots, bulb, dialog
├── src/
│   ├── content.json               # single source of truth, including the resume
│   ├── style.css                  # layout, components, Gruvbox themes, print styles
│   └── main.js                    # routing, dialogs, bulb, beforeprint resume, easter eggs
├── public/                        # copied as-is, outside the budget
│   ├── _headers                   # Cloudflare response headers (cache, optional CSP)
│   ├── og.png                     # generated by scripts/make-og.mjs
│   ├── resume.pdf                 # placeholder; print the site to replace it
│   ├── robots.txt
│   └── humans.txt
├── scripts/
│   ├── inline-assets.mjs          # inlines the built CSS and JS, fills the byte count
│   ├── build-404.mjs              # writes dist/404.html
│   ├── size.mjs                   # budget check
│   ├── make-og.mjs                # generates public/og.png, run once
│   └── make-resume-placeholder.mjs # regenerates the placeholder PDF
└── vite.config.js                 # renders tiles + JSON-LD + inline JSON from content.json
```

How `npm run build` fits together:

1. `vite build` renders the tiles, the navbar, the JSON-LD, and the inline JSON from
   `content.json`, and produces `index.html` plus separate CSS and JS files.
2. `scripts/inline-assets.mjs` folds the CSS and JS into `index.html`, fills in the real byte
   count on the "This site" tile, and deletes `dist/assets`.
3. `scripts/build-404.mjs` writes `dist/404.html`.
4. `scripts/size.mjs` checks both pages against the budget and fails the build if either is over.

Detail views and the resume are inlined as JSON and rendered by `main.js`, so they ship once
(Article II.3). `themes.css` isn't split out yet: Gruvbox lives in `style.css` until a second theme
exists.

## Benchmarking as we go

### 1. Every build: size gate (local, no dependencies)

`scripts/size.mjs` uses only Node's built-in `zlib` and checks every HTML page:

```js
import { readFileSync } from 'node:fs'
import { gzipSync, brotliCompressSync, constants } from 'node:zlib'

const LIMIT = 14_000, TARGET = 12_800
let failed = false

for (const file of ['dist/index.html', 'dist/404.html']) {
  const buf = readFileSync(file)
  const gz = gzipSync(buf, { level: 9 }).length
  const br = brotliCompressSync(buf, {
    params: { [constants.BROTLI_PARAM_QUALITY]: 11 },
  }).length
  console.log(`${file}  raw ${buf.length}  gzip ${gz}  brotli ${br}  (target ${TARGET}, limit ${LIMIT})`)
  if (gz > LIMIT) { console.error(`✗ ${file} over 14kb budget`); failed = true }
  else if (gz > TARGET) console.warn(`! ${file} over working target`)
}

if (failed) process.exit(1)
```

```jsonc
// package.json
"scripts": {
  "dev": "vite",
  "build": "vite build && node scripts/inline-assets.mjs && node scripts/build-404.mjs && node scripts/size.mjs",
  "size": "node scripts/size.mjs"
}
```

Cloudflare runs `npm run build`, so **a build over budget fails, and nothing gets deployed**. To
check by hand: `gzip -9 -c dist/index.html | wc -c`.

### 2. Every pull request: byte report

Cloudflare's build log for each pull request preview shows the `size.mjs` output. Copy the number
into the pull request description along with the change from `main` (Article II). An optional
GitHub Actions job can post it automatically later.

### 3. After deploying: check the real response

```sh
curl -so /dev/null -H 'Accept-Encoding: gzip' \
  -w 'body %{size_download}B  headers %{size_header}B  ttfb %{time_starttransfer}s\n' \
  https://<domain>/
```

`size_download` is the compressed size actually sent. `body + headers` must stay under about
14.6kb. Run this after any change to Cloudflare settings too, because injected scripts don't show
up in the local size check.

### 4. Confirming the single round trip

- **Chrome DevTools → Network:** select "Slow 4G", disable the cache, and reload. The document
  should be the only request before first paint.
- **[WebPageTest](https://www.webpagetest.org/):** the connection view shows the HTML arriving in
  a single burst after the TLS handshake.
- **[`sirupsen/initcwnd`](https://github.com/sirupsen/initcwnd):** shows the host's actual initial
  congestion window, which is how much data the server sends in the first round trip. Cloudflare
  allows about 40kb. Keeping to 14kb means the site stays a single round trip on any host.

### 5. Lighthouse

- Locally: `npx lighthouse <url> --view`. Use `npx` only, and never add it to `package.json`.
- Online: [PageSpeed Insights](https://pagespeed.web.dev/) on the pull request's preview URL or
  the live site.

## Deployment: Cloudflare

### Setup (Git integration)

1. Push the repo to GitHub and connect it in the Cloudflare dashboard (Workers & Pages → Create →
   import a repository). Workers static assets is Cloudflare's current recommendation. Pages also
   works.
2. Build command: `npm run build`. Output folder: `dist`. Vite `base: '/'`.
3. Every push to `main` deploys, and every pull request gets its own preview URL.
4. Hash routing means the SPA needs no rewrite rules.

### Custom domain

1. Register the domain through Cloudflare Registrar, which charges the registry price, or move an
   existing domain's nameservers to Cloudflare.
2. Attach it to the project under **Custom domains**. DNS records and the HTTPS certificate are
   set up automatically.
3. Update the canonical URL, Open Graph URLs, and JSON-LD `url` in `content.json`. Then update the
   resume, LinkedIn, and GitHub profile so all of them point to the same URL.

### Cloudflare rules

- Cloudflare MUST NOT inject anything into the page. Keep these turned off:
  - Rocket Loader;
  - Email Address Obfuscation, which injects a script and hides the plain-text email address;
  - automatic Web Analytics injection;
  - any HTML rewriting features.
- `public/_headers` sets long `Cache-Control` for `og.png` and `resume.pdf`, plus an optional CSP.
  `index.html` keeps a short cache time so changes show up quickly.
- Brotli is a bonus, not part of the budget.

### Fallback: GitHub Pages

The repo stays deployable to GitHub Pages:

1. Use a GitHub Actions workflow (`actions/upload-pages-artifact` + `actions/deploy-pages`) that
   runs `npm run build`.
2. Use a `<user>.github.io` repo or a custom domain (`base: '/'`). A project site needs
   `base: '/portfolio/'`.
3. For a custom domain, add a `public/CNAME` file and the GitHub Pages `A`/`AAAA` DNS records, and
   verify the domain in GitHub first so no one else can take it over.
4. Limitations: no custom headers, gzip only, and a 10-minute cache.

## Proposed amendments (draft, not yet approved)

Written up for review before any code changes, per [Amendments](#amendments). Nothing here is in

### Amendment A (draft): five tiles, and the name in the hero

**Why.** Seven tiles all carry the same visual weight, so nothing reads first and there is no entry
point for a quick skim. Tim's name is not in the hero, which is the first thing most visitors look
for. Focus and Contact are the two weakest tiles: Focus is three lines the headline already
implies, and Contact duplicates the navbar and the hero.

**Change Article VII.1 to five tiles:**

| Tile | Shows without clicking | Click-in |
|---|---|---|
| **Hero** | **Tim Radtke**, the page's main heading; role label; data-systems headline; availability · capacity · efficiency as one line; remote/location; email plus GitHub and LinkedIn | — |
| **Experience** | Current role at AMOpportunities and area of responsibility | Full history |
| **Skills** | Backend, frontend, data, infrastructure, and agentic tooling | Grouped detail |
| **Now** | What Tim is currently building, learning, or reading | Optional longer note |
| **This site** | Shrinks to a footer line: "N bytes and one round trip" | How it was built and why |

**Also change:**

- Article I.5: the hero leads with the name as the page's largest text, then the role label, then
  the data-systems headline.
- Article VII.3 still holds, and gets stronger: the hero alone answers who, what, and how to reach
  him.
- Article VII.2: five tiles leaves room for up to three project tiles inside the eight-tile cap.
- Article VIII.1: the navbar is unchanged. Resume · GitHub · LinkedIn · Contact stays.
- Article III is unaffected: the same content, redistributed.

**Byte estimate.** Dropping two tiles and adding one footer line is close to neutral. The name
heading is a few bytes. No change to the budget expected.

**Open in this draft:** whether the hero gets a small inline SVG mark, and whether "This site"
stays a real tile on phones, where a footer line has less room to explain itself.

### Amendment B (draft): give Gruvbox some depth

**Why.** The palette is used as orange plus a green byte count. Gruvbox has eight accents. One
accent per section makes the page faster to scan and makes the navbar ↔ tile link (Article VIII.2)
legible by color instead of only by border.

**Change Article VI and Article IX.4 to add:**

1. Each section has one accent, set as a CSS variable on its tile, from the Gruvbox palette:

   | Section | Accent | Dark | Light |
   |---|---|---|---|
   | Experience | blue | `#83a598` | `#076678` |
   | Focus | aqua | `#8ec07c` | `#427b58` |
   | Skills | purple | `#d3869b` | `#8f3f71` |
   | Now | yellow | `#fabd2f` | `#b57614` |
   | This site | green | `#b8bb26` | `#79740e` |

2. The accent shows in three places: a short rule at the top of the tile, the tile's "more" link,
   and the navbar mirror. Components still reference variables only (Article IX.4).

3. **Only text-safe accents may color text.** Measured contrast, on the tile surface, so this is
   evidence rather than a guess (Article IX.5):

   | Accent | Dark on `#32302f` | Light on `#f9f5d7` | AA text (4.5) | Non-text (3.0) |
   |---|---|---|---|---|
   | orange | 5.20 | 5.56 | yes | yes |
   | blue | 4.88 | 6.00 | yes | yes |
   | purple | 4.78 | 6.12 | yes | yes |
   | aqua | 6.24 | 4.53 | yes | yes |
   | yellow | 7.74 | 3.43 | **no in light** | yes |
   | green | 6.36 | 4.42 | **no in light** | yes |
   | red | 3.82 | 7.83 | **no in dark** | yes |

   All of them clear 3:1 in both modes, which is the bar for non-text marks (a rule, a dot, a

5. Optional, later: Gruvbox Material as a second theme, inside Article IX.7's 250-byte budget.

**Byte estimate.** Roughly 300–500 gzipped bytes for the extra variables and rules, out of the
6.4kb of headroom. Confirmed by the build when implemented, and reported per Article II.

**Open in this draft:** whether the accent also tints the tile border on hover, or stays on the

### Amendment C (applied): focus does not reuse hover

**Why.** When a dialog closed, the browser returned focus to the link that opened it. The tile
style was tied to `:focus-within`, so the tile stayed in its hover look, and hovering a second tile
left two tiles looking open at once.

**Applied:** Article VIII.2 and Article XII.1 now say hover styles are not reused for focus.
Keyboard focus stays visible through the standard `:focus-visible` ring on the focused control,
which is a focus indicator rather than an imitation of hover. The alternative was to keep the
focus mirror and accept a lingering highlight, which is the bug being fixed.
